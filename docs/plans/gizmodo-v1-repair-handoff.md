## 4. 先确定的状态与接口约定

本节是推荐实现契约，当前代码尚未提供这些新增字段和接口。实现时可采用等价方案，但必须满足后续所有验收条件，并在修复记录中写明实际契约。

### 4.1 身份与持久化状态

- `task_id`：稳定文件任务身份，实际重新识别也不改变。
- `attempt_id`：一次真实执行身份；重新识别产生新 ID，单纯重新保存沿用原 ID。
- `history_id`：已经成功提交的历史记录 ID。保存失败时为 null，不能复用上次结果 ID。
- 临时结果可预分配候选记录 ID，但未成功提交前不得把它放进表示“已保存”的 `history_id`。
- `result_version`：同一任务的执行结果版本。队列实际执行前预留并持久化，保存失败也不释放该版本；允许版本有空缺。旧记录缺失时按 1 读取。旧临时数据暂时无法确定版本时可以为 null，但提交前必须核对原 attempt，不能按重试保存的时间分配“最新”版本。

预留版本时同时考虑该任务已保存的版本、队列中的版本上界和保留的 pending attempt。新任务重试应先成功持久化 attempt/版本预留，再开始昂贵识别；磁盘已经无法写入该状态时，暂停并报告原因。单纯重试保存保持原 attempt、生成时间和版本。这样可防止较早失败的结果晚保存时反而覆盖较新的结果。

建议保留现有 `queued/running/done/error/cancelled` 调度状态，新增正交的保存状态，避免把可读性、完整性和执行状态混为一个 status：

```ts
type PersistenceState = "pending" | "saved" | "failed" | "unavailable";

type ResultRef =
  | { kind: "history"; historyId: string }
  | { kind: "temporary"; taskId: string; attemptId: string };
```

队列/批次只返回轻量字段：`attempt_id`、`persistence_state`、`history_id`、`temporary_result_available`、`source_available`，以及可选的 `can_retry_save`。全文仍按打开结果时获取。

建议统一计算这些能力：

| 能力/计数 | 条件 |
| --- | --- |
| 可长期回访的完整结果 | 已成功保存、history_id 有效、integrity=complete。 |
| 可预览 | 已保存结果存在，或当前 attempt 有可读临时结果。 |
| 可重试保存 | 保存失败，且当前 attempt 的临时 payload 仍可读。 |
| 可重新处理 | 当前允许重试且真实暂存来源存在。 |
| 可完成清理 | 明确已完成且没有待恢复的保存失败结果；取消/失败项不能顺带删除。 |

### 4.2 阅读与播放位置

保留旧 `read_position` 的秒数兼容接口，新增彼此独立的字段：

```ts
interface ReaderPosition {
  segment_index?: number;       // 有 segments 时的锚点
  text_offset?: number;         // 纯文本时的字符锚点
  within_block_ratio?: number; // 锚点块内位置，0..1
  scroll_ratio?: number;       // 最后回退，0..1
}
// history 记录及 PATCH /api/history/{hid}/view：
// reader_position?: ReaderPosition
// playback_position?: number  // 秒
// position?: number           // 旧客户端兼容
```

新客户端播放时不再被页面滚动写入的秒数覆盖。老记录缺少新字段时，继续利用 `read_position` 定位 segment/音轨，不能要求用户迁移全部历史。

### 4.3 时间能力

建议结果记录增加：

```ts
interface TimingInfo {
  level: "word" | "segment" | "none" | "unknown";
  source: "forced_alignment" | "asr" | "unknown";
  alignment_requested: boolean;
  alignment_succeeded: boolean;
  fallback_reason?: string;
}
```

`alignment_succeeded` 表示实际流程成功，`level` 表示结果中实际可用的数据粒度。强制对齐后经过 `resegment_words` 得到句段时，输出 cue 仍是 segment；不能仅由 `aligner_used=true` 宣称返回的每段都是词。

导出生成的整段粗略 cue 单独标为 `coarse`，这是导出能力，不得回写成 ASR 实际提供了段级时间戳。

## 5. A01：消除导入中的静默丢项

## 8. A04：保存失败后的可读结果与恢复

**位置：** `main.py:transcribe` 两个历史保存分支、`queue_api.py:process_next_once/queue_retry`、`queue_store.py`、批次聚合和 reader/export。

### 8.1 结果产生与历史提交

1. 在识别结果产生后形成完整的待提交 payload，包含 text、segments、stats、任务/批次/来源、alignment/timing 和生成时间。
2. 使用实际执行前已经预留的 attempt/版本，形成候选记录身份，复用同一 payload 进行保存重试；不要在每次保存重试中重复生成识别结果、时间或版本。
3. 将历史写入统一为同目录临时文件写完后 `os.replace` 原子提交。坏的半份 JSON 不能被历史列表当成完整结果。
4. 提交成功后再报告有效 history_id。若成功响应丢失或队列状态提交失败，重试按 attempt/候选 ID 识别已保存记录，返回同一 history_id。
5. 同一任务真实重跑才产生新 attempt/新结果版本。保存重试不占 GPU 识别槽、不重跑 ASR、不创建重复版本。

### 8.2 临时结果管理

新增独立 PendingResultStore：

- 队列摘要不保存整份正文，继续满足 queue.json 的 10 MiB 读取上限与轻量轮询约束。
- 保存失败后立即保留当前会话内可读 payload，并尝试写入独立 `data/pending_results/` 恢复文件。
- 如果磁盘已满，恢复文件也可能写入失败；仍保留内存结果和已存在的源文件。界面明确说明“本次会话可读，尚未持久化；关闭后可能丢失临时文字，可从保留原文件重新处理”。
- 临时结果采用按实际字节数限制的容量管理。达到上限时暂停启动新任务并提示恢复/释放，不能静默淘汰唯一可读的失败结果。
- 清理 worker 的局部变量、临时音轨目录或队列完成项时，不能释放唯一结果副本。
- 保存成功并完成关联后，才删除对应恢复 payload；取消项是否保留源文件继续遵循已有重试规则。
- 显式删除任务可以删除其临时结果和来源，但要明确告知影响。完成清理不能把保存失败项当作普通 done 删除。

### 8.3 调度状态与恢复动作

推荐状态约定：

| 场景 | status | persistence_state | 动作 |
| --- | --- | --- | --- |
| 识别成功且历史已提交 | done | saved | 查看、导出、正常归档。 |
| 识别成功但保存失败 | error，error=history_save_failed | failed | 查看临时结果、重试保存、从原文件重跑。 |
| 取消但有部分结果，保存失败 | cancelled，附保存错误 | failed | 查看临时部分结果、重试保存、从原文件重跑。 |
| 取消且没有文字 | cancelled | unavailable | 保留来源，允许从头重跑。 |
| 旧数据为 done + history_save_failed | 读取时归一化或受控迁移 | failed | 按实际 payload/来源可用性提供动作，不伪称可恢复已删除数据。 |

建议新增：

- `GET /api/queue/items/{qid}/result`：按当前 attempt 获取临时/已保存结果，不在轮询中调用。
- `POST /api/queue/items/{qid}/save`，请求携带 `attempt_id`：只重新提交该结果。
- 旧 `POST /retry` 保持“从原文件重新识别”的语义；与“重新保存”按钮分开命名。

保存接口按任务/attempt 加锁，返回当前保存状态和 history_id；过期 attempt 返回冲突，临时结果已不存在返回明确的不可用状态。重复点击和并发请求只产生一份历史。

Reader 使用 ResultRef 解析临时结果，不拿假 history_id 调历史接口。临时结果标题和导出入口必须标注尚未保存；默认的“完整且已保存”批量交付范围不混入临时结果。如允许临时结果单独导出，需显式选择并在清单中标记保存状态。

临时结果保存成功后，更新其保存身份和能力，不重建当前 reader/audio 会话；会话 key 可以保持为稳定 attempt 身份。用户已开始新的执行时，旧 attempt 的保存请求不能覆盖当前任务关联；默认返回冲突。若未来支持保存为旧历史版本，必须沿用原版本身份，并与“设为当前结果”分开。

### 8.4 进程重启与失败边界

1. 将 attempt 身份在实际识别开始前写入队列。新 attempt 不能继承上次 history_id 来代表新结果。
2. 重启时先检查当前 attempt 是否已经提交历史；若已提交，修复队列关联，不再次识别同一 attempt。
3. 若有可读恢复文件，恢复“保存失败、可预览/重试保存”的状态，不自动从头覆盖它。
4. 若只有原文件、没有可读临时结果，明确文字未恢复，提供从头重跑；不展示“已有部分结果”。
5. 历史提交成功、队列关联失败时，保留源文件到关联持久化成功后再清理。
6. 模拟 HistoryStore 写入失败时也要验证 QueueStore 写入可能同时失败；至少保持进程内可读结果和原文件，错误处理本身不能再次抛错丢掉 payload。

### 验收

历史写失败、恢复文件写失败、队列写失败、保存成功但响应丢失、连续重试、并发重试、取消后的保存失败、保存中关闭重开都要测试。原失败用例 `test_save_failure_keeps_source_recoverable` 必须通过；不能仅修改断言规避问题。成功数不含保存失败项。

## 15. 可复现的隔离验证流程

### 15.1 前端构建

从仓库根目录开始，使用现有依赖：

```powershell
Push-Location frontend
```

### 15.2 建立新的测试副本

以下示例只复制源码、生产构建及测试，不复制用户 data、模型或整个旧验收目录：

```powershell
$repoRoot = (Get-Location).Path
$verifyRoot = Join-Path $repoRoot 'build\acceptance-repair-20261030-r1'
```

### 15.3 后端回归

真实 llama-server 先关闭，再运行模拟启动测试；上一轮真实 8080 模型服务与 mock 启动测试并行曾产生端口干扰。
